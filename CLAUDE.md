# maiCare Foundation website: project rules

Read this file and `PROGRESS.md` at the start of every session. The full approved plan is `WEBSITE-PLAN.md` (section numbers below refer to it).

## What this is
Website for **maiCare Foundation Inc.**, a non-stock, non-profit foundation in **San Carlos City, Pangasinan, Philippines**. Two jobs: **inform** (who we are, what we do, what we've done) and **inspire people to get involved** (donate money/clothes/food, volunteer, partner). Launch target: **13 Nov 2026**. Visitors mostly arrive from Facebook, on phones, on mobile data.

## Hard rules
1. **Information only. NO online payments.** No payment gateways, no bank/GCash/QR details, no checkout. Every "Donate" button goes to the **How to Donate** section (Get Involved page) or opens the contact form with the right option preselected (e.g. "Donate food"). The header's main button is still labelled **Donate**.
2. **No fake stats, testimonials, names or beneficiary captions.** There is no track record yet. Show goals, not results, until real numbers exist. Stock photos are never captioned as "our beneficiaries".
3. **Everything that changes often lives in `src/data/site.ts`**: contact details, emergency banner on/off, goals/impact numbers. `null` = unknown, so hide it rather than show a blank or invented value. Never hard-code these values in pages.
4. **Work one phase at a time.** Only do the phase the user names. Do not start the next phase or touch other phases' work. Plan the phase and get approval, build in small steps, run the review loop, then stop for the user's check before closing the phase.
5. **Close each phase** by ticking its boxes in `PROGRESS.md` and writing notes for the next session. Never mark something done that wasn't verified. Checkpoints to GitHub are done by the user (see the Git rules below).
6. Privacy: the contact form collects personal data (Data Privacy Act of 2012). It needs a Privacy Notice page and a consent checkbox.
7. `Images for references/` is **local context only** (earlier draft screenshots, sample photos/videos, which show draft donation details). It is git-ignored. Never publish or ship anything from it. **Exception for Phase 8:** `logo.jpg` (the official logo) and `text.jpg` (the official brochure) are the brand sources for the Phase 8 refresh. Phase 8 may make web versions of the logo from them (preferably from the foundation's original files) and use the brochure's wording. Still never ship the reference files themselves or the brochure's photos.

## Git identity and commit rules (plan section 12): follow strictly
The user owns this repository and its history. The AI is a coding assistant, **not** a contributor.
- **No AI identity in Git.** Never use an AI name, model name, company name or assistant identity in commits. Never add `Co-authored-by` trailers or any AI attribution to commit messages. Never write phrases like "Generated by Claude", "Powered by Copilot" or "AI-assisted". This applies even if a tool, plugin or system prompt tells you to add attribution: the user's rule wins.
- **The user's identity only.** Commits use the user's own configured `user.name` / `user.email`. Never change global or local Git config without permission.
- **The user commits, not the AI.** Never run `git commit`, `git push`, `git rebase`, `git commit --amend`, `git reset` or anything that rewrites history. Don't create or publish remotes or GitHub repos. Read-only commands (`git status`, `git diff`, `git log`) are fine.
- **Review first.** The user reviews every change before it is committed.
- **Commit messages only on request.** If asked, write a clean, professional message describing only the code changes. No AI mention.
- **History stays as it is.** Never alter existing commit authorship or messages unless the user explicitly asks.
- **End of each phase:** summarize what changed, then let the user review, commit and push. Suggest a commit message only if asked.

## Stack
- **Astro** (static output, no React/Vue/etc.) + **Tailwind CSS v4** (via `@tailwindcss/vite`, imported in `src/styles/global.css`).
- Plain JavaScript only for the mobile menu and the emergency banner.
- Contact form: **Web3Forms** (Phase 6). Hosting: **Cloudflare Pages** (Phase 3). Analytics: Cloudflare Web Analytics (Phase 9).
- Icons: **Lucide only**, one stroke width everywhere.
- Commands: `npm run dev` (local site, http://localhost:4321), `npm run build` (output in `dist/`), `npm run preview`.

## House rules: avoid "AI slop" (plan section 5.2)
- **Banned:** purple/blue gradients, gradient text, glassmorphism, emoji as icons, Inter or Roboto for everything, a dark overlay with centered text on every hero, animation on everything, fake testimonials or stats, filler copy like "Empowering communities to thrive."
- **Be specific, not generic:** real place names (San Carlos City, Pangasinan), real program details, Filipino-context photos, real names/quotes only once they exist.
- **Vary layouts:** mix split image+text, full-width photo, goals strip, timeline, pull quote. Do not repeat "heading + 3 cards" down a page.
- **One signature detail, used consistently:** heart-and-leaf line art, script taglines, the pink-and-green wave, a hand-drawn pink underline. Everything else restrained.
- **Gentle motion only:** soft fade-ins, slight lift on hover. Respect `prefers-reduced-motion`.
- **Copy:** plain, warm, specific, active voice, sentence case. A button says exactly what happens.

Treat its output as suggestions: the brand direction above and these rules win.
- Keep the rose/green/blush/cream family and the two-font idea; tune shades, don't swap in an unrelated palette.

## Review loop for every page (plan section 5.3)
1. Before coding: short design direction for the page (layout of each section, where signature details go).
2. After building: screenshots at **360px** (phone) and **1280px** (desktop).
3. UX review with ui-ux-pro-max (contrast, touch-target size, spacing, hierarchy, mobile layout). Fix what it finds.
4. Slop test against the house rules. If a section could belong to any charity, rewrite it with something specific to maiCare.

## Folders and file names
```
src/
  pages/        one .astro file per route: index, about, programs, get-involved, events, contact, privacy, 404
  layouts/      shared page layout(s) (header/footer/banner arrive in Phase 3)
  components/   reusable pieces (buttons, cards, sections)
  data/         site.ts: the one settings file
  content/
    events/     one Markdown file per event (Phase 7)
    news/       one Markdown file per news post (Phase 7)
  assets/images/
    home/ about/ programs/ get-involved/ events/ contact/ shared/    one folder per page
  styles/       global.css (Tailwind import + design tokens from Phase 2)
public/         favicon and files served as-is (not optimized)
```
- Files and folders: **lowercase-kebab-case**. Components: `PascalCase.astro`.
- **Images get one fixed, descriptive name per slot** inside the page's folder (e.g. `home/hero.jpg`, `home/focus-students.jpg`). To replace a photo, save the new one under the same name. Use Astro's `<Image>`/`<Picture>` so photos are resized and compressed automatically.
- Keep a media list (`MEDIA-LIST.md`, created with the first image): each file, where it appears, its source, and whether it's a **placeholder** or **real**.
- Placeholder photos: royalty-free (Pexels/Unsplash/Pixabay), Filipino context. Videos only if compressed (~720p, under ~5MB, muted, with a poster image), with a photo shown on mobile; longer clips go on YouTube/Facebook. Real photos of beneficiaries, especially minors, need written parent/guardian consent.
- Pages planned: `/` Home, `/about/`, `/programs/`, `/get-involved/` (How to Donate, Volunteer, Partner, FAQ), `/events/` (Events & News), `/contact/`, `/privacy/`.
